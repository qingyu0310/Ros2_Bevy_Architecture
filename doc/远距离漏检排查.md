# 远距离漏检排查

现象：3 m 外两块装甲板只稳定检出其中一块，剩下那一块逐帧闪；被闪掉的那一帧跟踪器只有一条匹配，
瞄准面被无条件改写，于是出现约 0.3 m、0.55 s 周期的瞄准点切换。

本文从采集分辨率开始逐级量下去，每一级给出**当前值、算出来的期望值、判据和验证方式**。
按顺序查：后一级的输入是前一级的输出，跳过任何一级都会把原因归错地方。

---

## 0. 数据链与各级的落点

```
仿真 1440×1080 rgb8  →  camera 节点转 bgr8  →  detector：等比缩到 640×640 左上角 → TensorRT 0526
   → 后处理逐级门限 → DetectedArmor → 按 enemy_color 过滤 → 跟踪器四门关联 → 瞄准面选择
```

| 级 | 文件 | 关键符号 |
|---|---|---|
| 采集 | `third_party/bevy_robomaster_simulator-master/config.toml` | `[capture.color] width/height`、`[camera] fov` |
| 内参 | `.../src/capture.rs` | `compute_camera_intrinsics` |
| 编码 | `ros2_layer/node/camera/camera_node.hpp` | `on_image` |

| 后处理 | 同上 | `Postprocess`（第 495 行） |

## 1. 采集与内参：一块板在相机里有多少像素

### 当前值

`config.toml`：

- `[capture.color] width = 1440`、`height = 1080`
- `[camera] fov = 45.0`（度，垂直视场）

`compute_camera_intrinsics` 的定义（`src/capture.rs:145`）：

```rust
let aspect = width / height;
let fov_x  = 2 * atan(tan(fov_y / 2) * aspect);
let fx = width  / (2 * tan(fov_x / 2));
let fy = height / (2 * tan(fov_y / 2));
```

代入 1440×1080、45°：

```
fov_y = 45°            → tan(22.5°) = 0.41421
fy    = 1080 / (2 × 0.41421) = 1303.6
aspect = 1.33333       → tan(fov_x/2) = 0.41421 × 1.33333 = 0.55228
fx    = 1440 / (2 × 0.55228) = 1303.6
cx = 720, cy = 540
```

日志里 `observed xyz_cam=(-0.254, 0.251, 3.043)` 这类距离与像素位置也对得上这个内参
（`u = fx·x/z + cx`）。

### 一块小装甲板在整图上的宽度

小装甲板宽 `0.135 m`（`armor_pose.hpp` 的 `kSmallArmorWidthM`）。正对相机、距离 `d`：

```
w_px = 0.135 / d × 1303.6
```

| 距离 | 正对 | 斜看 45°（×cos45°）|
|---|---|---|
| 1.5 m | 117 px | 83 px |
| 3.1 m | **56.7 px** | **40.1 px** |
| 4.5 m | 39.1 px | 27.7 px |

### 判据

- 正对时 `w_px ≥ 30 px`、斜看时 `≥ 25 px`：检测应该在 0.9 以上稳定
- 低于 25 px：置信度会掉到 0.8 门限附近，逐帧闪属于正常现象，不是跟踪器的 bug

**日志实测**：3.1 m、`conf=0.88~0.89`；1.5 m 时 `conf=0.95~0.97`。结论：这一级已经到分辨率极限，
但还没到"必然漏检"的程度，需要看下一级缩放又损失了多少。

### 验证

```bash
ros2 topic echo /vision/camera_info --once
# 期望 K = [1303.6, 0, 720, 0, 1303.6, 540, 0, 0, 1]，width=1440, height=1080
```

## 2. 预处理：640×640 之后还剩多少像素

### 当前做法

`armor_detector.cpp:431` 的 `Preprocess`：

```cpp
const double scale = std::min(640.0 / cols, 640.0 / rows);   // 1440×1080 → 640/1440 = 0.44444
canvas.setTo(0);                                              // 整张画布先清零
resize(bgr_image, canvas(Rect(0, 0, 640, 480)), ...);         // 等比缩放到左上角，不居中、不 letterbox
blobFromImage(canvas, chw, 1/255, Size(), Scalar(), true, false, CV_32F);
```

`cols/rows = 1440/1080`，所以 `scale = 640/1440 = 0.44444`，缩放后是 **640×480**，下面 160 行全是补的 0。

### 一块板进网络后的宽度

```
w_net = w_px × 0.44444
```

| 距离 | 正对 | 斜看 45° |
|---|---|---|
| 3.1 m | 25.2 px | **17.8 px** |
| 4.5 m | 17.4 px | 12.3 px |

### 判据

- `w_net ≥ 24 px`：这是 0526 训练分布里的常见尺寸，稳定
- `16 px ≤ w_net < 24 px`：处于 recall 开始掉的区间，正是日志里的工作点
- `w_net < 16 px`：漏检是必然的，调门限也没用

**当前 3.1 m 斜看是 17.8 px，落在掉 recall 的区间。**

### 可回收的部分

画布只用了 `480/640 = 75%` 的面积。若改成按高度铺满并居中（letterbox）：

```
scale = 640/1080 = 0.59259，缩放后 853×640，左右各补 106 列
w_net = 56.7 × 0.59259 = 33.6 px（3.1 m 正对）
```

比现在多 33%。**代价**：与训练时的预处理不一致，如果 0526 是用"左上角补零"训练的，改了会掉精度。
这一项必须先确认训练侧的做法，不能直接改。

### 验证

在 `Preprocess` 里临时打印一次 `resized_width / resized_height / scale`：

```cpp
RCLCPP_INFO(...) // 或 std::printf
```

期望 `scale=0.4444`、`resized=640×480`。若不是这个数，说明分辨率或输入尺寸和本文假设不一致。

## 3. 后处理门限：每一级丢了多少

### 当前值

`project/params/vision.yaml`：

- `score_threshold: 0.7` —— NMS 前的 objectness 初筛（`armor_detector.cpp:515`）
- `confidence_threshold: 0.8` —— NMS 后的终选（第 589 行，**严格大于**）
- `nms_threshold: 0.3`

`ArmorDetectionStats` 已经记了每一级：

```
raw_rows / score_passed / nms_kept / accepted
rejected_confidence / rejected_color / rejected_label_type / rejected_geometry
max_objectness
```

但 `log_window`（`vision_node.cpp:515`）**只打印了 `accepted` 的累加**，其余字段一个都没输出。
所以现在无法判断"远处那块板是没进 NMS、还是被终选门限挡了、还是颜色分错了"。

### 这一级要加的诊断（一次性加全）

在 `log_window` 每秒汇总里，把本秒累加的各级计数打一行：

```
det stats raw=%zu score_pass=%zu nms=%zu accepted=%zu | rej conf=%zu color=%zu label=%zu geom=%zu | max_obj=%.2f
```

再加一条**单帧漏检检测**：一帧里 `enemy_armors.size()` 从 2 掉到 1 时立刻打印，
而不是等每秒汇总（汇总里看不出来，日志里 `detections=3` 的那几秒恰好都是两块齐全的）。

判据：如果 `rejected_confidence` 在远处每秒涨几十，说明是终选门限；
如果 `score_passed` 本身就是 0，说明卡在初筛或网络直接没给出高 objectness。

### 先做的低成本试验（不用编译）

把 `confidence_threshold` 从 0.8 降到 0.75，`score_threshold` 保持 0.7（终选不能低于初筛，
`ValidateConfig` 会拒绝 `confidence_threshold < score_threshold`）。

- 若远处切换明显减少 → 确认是终选门限
- 若没变化 → 掉在初筛或网络，往上一级查

## 4. 颜色与标签过滤：是不是被当成别的类别

### 当前做法

- `DecodeArmorModelColor`：只接受 `0=Blue`、`1=Red`，其余算 `rejected_color`
- `enemy_color: "blue"`：视觉节点在 `vision_node.cpp:192-201` 只把蓝色送进跟踪器
- `DecodeArmorModelSize` + `IsArmorLabelCompatibleWithSize`：标签与尺寸不自洽算 `rejected_label_type`

### 关键风险

远处板子只有 18 px 宽，颜色分支（`row[9..13]`）与标签分支（`row[13..22]`）的 argmax 在小目标上最容易翻。
如果某帧把 `label=2` 判成 `label=3`，跟踪器的 `Associate` 会因为 `armor.GetLabel() != label_`
直接把它当**别的车**拒掉——日志里表现为 `candidates=1`，看起来和"漏检"完全一样。

### 怎么区分

看 `try` 诊断（`vision_node.cpp:553` 起）里的 `cand=` 与 `det_center=`：

- `candidates=1` 且只剩的那块是原来的 cand0 → 另一块**根本没送进跟踪器**（检测或颜色/标签阶段丢了）
- `candidates=2` 但 `matches=1` → 送进来了但被四门拒了，问题在关联

日志里两种都出现过：
- `4184.969`: `candidates=2 matches=2`（两块都在）
- 切换前的帧看不到，因为每秒只汇总一次

### 要加的诊断

`on_image` 里在过滤前后各打一次（仅当 `result.armors.size() != enemy_armors.size()` 时）：

```
det raw colors: n=2  blue/label2/size0  blue/label3/size0  | enemy_color=blue → kept 1
```

## 5. 跟踪器：为什么单板帧会改写瞄准面

### 当前逻辑

`tracker.cpp:167`：

```cpp
const std::int32_t aim_index = SelectAimMatch(association.matches, dimensions, camera);
```

`SelectAimMatch`（第 198 行）：

```cpp
score = AimMatchScore(match) + (match.face == report_.last_face ? 0.0 : aim_switch_cost);
```

`aim_switch_cost: 5.0`，`AimMatchScore` 的三项之和在日志里是 0.1~0.4 量级，所以罚值足够大。

**但**：`matches.size() == 1` 时，循环里只有一个候选，罚值加不加都返回它，
第 182 行 `report_.last_face = match.face;` 无条件改写。

### 用日志核对

从一份 3.1 m 的日志里统计（每 0.55 s 一次切换）：

| 时刻 | target_map | face |
|---|---|---|
| 184.307 | (-3.026, -0.197) | 0 |
| 184.319 | (-2.754, -0.080) | 3 |
| 184.853 | (-3.036, -0.234) | 0 |
| 185.518 | (-2.755, -0.086) | 3 |
| 186.076 | (-3.033, -0.294) | 0 |

两簇相距 `0.301 m`（face0 与 face3 的间距），与 `√(r²+(r+l)²)` 一致：
`r=0.1885`、`l=0.047` → `√(0.1885² + 0.2355²) = 0.302 m`。

切换都发生在两次汇总之间，而汇总帧本身都是 `candidates=2 matches=2`——
说明切换不是双板帧里罚值没压住，而是中间**有某几帧只有一块板**。

### 判据

- 若在 `candidates=1` 的帧上切换 → 确认是单板帧改写，根因在检测（第 2~4 节）
- 若在 `candidates=2` 的帧上切换 → 罚值量级不对，要查 `AimMatchScore` 三项的实际数值

## 6. 时序：图像与姿态对齐是否也在贡献

### 当前值

- `pose_missing` 每秒 3~22 次（78 fps 下 4%~28%）
- `pose offset avg` 在 -5~+9 ms，`min/max` 在 -30~+68 ms，`hold=30 ms`

姿态缺失的帧整帧跳过（`vision_node.cpp:242-252` 早期返回），不推进跟踪器。
`dt` 已改成"距上一次真正调用 `ProcessFrame`"（`vision_node.cpp:225-234`），所以缺帧不再欠预测。

### 判据

`pose offset max` 超过 `hold=30 ms` 的次数若持续很多，说明 TF 发布频率低于图像帧率太多，
可以考虑把 `pose_hold_s` 调到 0.05 或者提高仿真 TF 发布频率。但这只影响瞄准点抖动，
**不会造成整块板漏检**，所以排在检测之后。

## 7. 排查顺序与预期结论

按代价从低到高，每一步都能独立下结论：

| 步 | 动作 | 期望 | 若不符 |
|---|---|---|---|
| 1 | `ros2 topic echo /vision/camera_info --once` | `fx=fy≈1303.6`、1440×1080 | 分辨率/FOV 与本文假设不一致，重算第 1 节 |
| 2 | 加第 3 节的 `det stats` 汇总行 + 单帧漏检打印（需编译） | 看到远处 `rejected_confidence` 或 `score_passed` 在掉 | 定位到具体哪一级 |
| 3 | `confidence_threshold: 0.8 → 0.75`（不编译） | 切换频率下降 | 还有别的级在丢，回第 2 步 |
| 4 | 加第 4 节的颜色/标签打印 | 远处是否有 `label` 翻转 | 有则属于模型小目标分类问题，不是门限 |
| 5 | 确认 0526 训练时的预处理 | 是否 letterbox | 若训练是整幅缩放，第 2 节的居中方案可省 |
| 6 | 放慢敌人转速或拉近到 2 m 复现 | 切换消失 | 确认与目标像素尺寸直接相关 |

**当前已有数据的倾向**：第 2 节算出的 17.8 px 落在 recall 的下降区间，第 3 节的逐级统计又是黑的，
所以下一步应该是**加统计**而不是调参数——否则调了门限也不知道是哪里变好的。

## 8. 验证与回退

- 每次只改一项（门限 / 预处理 / 诊断），其余不动
- 复现条件固定：敌车 > 3 m、两块板的 `label` 与 `size` 一致、`enemy_color` 与车色一致
- 记录：每秒切换次数（从 `aim cmd yaw` 的跳变数）、`detections=` 每秒的最小值、`conf` 最小值
- 回退：诊断代码只加打印、不改逻辑，验证完可以保留；参数改动改回 `vision.yaml` 原值即可
