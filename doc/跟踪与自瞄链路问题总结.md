# 跟踪与自瞄链路问题总结（2026-10-18）

本文按"问题 → 原因 → 解决 → 现在怎么跑"组织，覆盖从单装甲板不收敛到仿真云台乱飞这一整条链路。
涉及的代码全部在 `framework/algorithm/vision/track/`、`ros2_layer/node/vision/` 与仿真
`third_party/bevy_robomaster_simulator-master/src/` 内。

---

## 一、整条链路长什么样

```
仿真相机  /vision/image ──┐
仿真 TF   /tf ────────────┤
                          ▼
                    vision 节点
                     ├─ 检测：TensorRT 出装甲板四点、颜色、编号
                     ├─ 位姿：按图像时间戳从 /tf 缓冲里插值出 map←相机
                     ├─ 跟踪：VehicleEKF 估车心、转速、半径、四面
                     ├─ 解算：车心/板心 → map 系 → yaw/pitch
                     └─ 发布：/rm_gimbal/cmd（yaw, pitch, distance, fire_advice）
                          ▼
                    仿真 ROS2 插件
                     ├─ 收到 cmd → GimbalAimTarget（目标姿态）
                     └─ F5 打开后 PID 接管云台
```

两个坐标系要区分开：

- **map 系**：仿真 TF 的根，z 向上，装甲板和车心都在这个系里表达。
- **camera_optical_frame**：z 朝前、x 朝右、y 朝下，检测和 PnP 都在这个系里。
- 两者之间不是一条 TF 边，而是 `map → odom → gimbal_link → camera_link → camera_optical_frame`
  五级串起来的。

整条链上只有两个"时间"，图像时间戳和姿态时间戳；它们对不对得上，决定了跟踪框稳不稳。

## 二、问题一：单装甲板跟踪不收敛，半径恒为 0.200 m

**现象**：跟踪状态能进 tracking，但 `r` 永远是初值 0.200，框在小车自身转动时抖动，预测框和实测框
经常错开一整块板。

**原因有三层，逐层排掉：**

1. **单板本来就不该估半径。**
   状态是 11 维 `[cx, vx, cy, vy, cz, vz, a, w, r, l, h]`，一块装甲板只能给出这块板自己的位置和法向。
   车心沿板法向移动和半径变化在观测上完全等价——`r` 加多少、车心就退多少，四点像素一模一样。
   对 1、3 两面甚至只有 `r + l` 可观测。所以单板帧把 `r/l/h` 放进观测，只会让滤波器沿着一条
   零空间随意滑动，协方差看着在收敛，状态其实是错的。

2. **`estimate_shape` 是个死开关。**
   原来它作为配置项存在，但没有任何路径把它置真，于是形状永远不参与估计；
   后来改成"本帧匹配到 ≥2 个面才为真"，才让"多板同时可见"时真正约束形状。
   现在的判据就是 `association.matches.size() >= 2`。

3. **换目标时 NIS 历史没清。**
   `Reset()` 只清了状态，没清 `filter_` 里最近 100 次的 NIS 失败记录。旧目标攒下的失败率
   会直接算到新目标头上，新目标第一次更新就被判丢，表现是 `updates=1, state=lost` 反复重建。

**解决**：

- `VehicleEKF::Update(...)` 只在 `estimate_shape` 为真时把 `r/l/h` 加进观测状态列，并且只在
  这时调用 `ApplyLimits()`；过程噪声里这几个分量的方差也随之为 0。
- `Tracker::ResetTarget()` 统一负责丢弃目标，`VehicleEKF::Reset()` 里调用
  `filter_.reset_nis()`。
- 半径和第二半径的钳制（`ApplyLimits`）会把被钳掉的那部分不确定度还给协方差，
  避免"状态贴着边界跳、协方差却很小"的虚假置信。
- 增加"连续 5 次撞几何边界即判发散"与 NIS 失败率两条兜底，触发后回 lost 重建。

**关联部分**同时修了一个会放大问题的 bug：本帧匹配到两块相邻板（如 face 2、3）时，
"面序必须连续"的判据用错了环绕公式，导致两板的合法解被整体丢弃，永远只剩一块板更新。
现在改成沿四面环数一遍"空档段数"，恰好一段才算连续。

## 三、问题二：云台一转，框就飘

**现象**：小车不动、只转云台时，检测框本身没问题，但跟踪器预测的框和实际框错开，状态时好时坏。

**原因**：图像和姿态不是同时到的。跟踪器工作在 map 系，每帧要把相机系观测换成 map 系，
这个变换用的是姿态。如果拿"最新一条姿态"去配一张更早的图，云台在这段时间里转过的角度
就被当成"目标在动"，EKF 被喂进了一个假速度。

**排错过程中确认的事实**：

- `/gimbal_pose` 这个话题在仿真里是**硬编码的单位四元数**，只有 `frame_id` 有意义。
  拿它当姿态源，世界系永远不会随云台旋转——这条路直接排除。
- `/tf` 每条消息只带一条父子边，不能直接 `lookup("map", "camera_optical_frame")` 一条匹配。
- 日志里 `pose offset avg ≈ 0`、`point_map` 与仿真发出的 `armor_*` 只差几厘米，
  说明时间对齐和相机位姿链本身都是对的。

**解决**：

- 新增 `PoseBuffer`（`ros2_layer/node/vision/pose_buffer.hpp`）：按接收时刻存
  `map←camera` 的旋转和平移，容量 256 条。
- 每帧图像用**图像时间戳**去缓冲里查：找到夹住该时刻的前后两条，旋转做 SLERP、
  平移做线性插值。
- 图像通常比同一时刻的 TF 先到，目标时刻会略微超在最后一条之后。给一个 30 ms 的保持窗口
  （`pose_hold_s`），窗口内用最后一条顶替；超出窗口就**整帧丢弃**，不检测、不跟踪、
  不发布，也不推进预测。
- 丢帧计入 `pose_missing`，窗口日志里能看到丢了多少。

**为什么宁可丢帧**：用旧姿态换算观测，会把云台转动误当成目标运动，比少一帧更糟。
日志里 `pose_missing` 长期只有个位数，说明这个策略代价很小。

## 四、问题三：TF 链路怎么取才对

仿真发的 TF 树：

```
map
 └─ odom
     └─ gimbal_link
         ├─ muzzle
         ├─ camera_link
         │   └─ camera_optical_frame
         └─ armor_*
```

要点：

1. **必须逐级上溯。** 每条 TF 消息是一组"父 → 子"的边，节点里按 `child_frame_id` 建索引，
   从 `camera_optical_frame` 往上找父、再找父的父，一路乘到 `map`。超过 16 级就放弃，
   防止异常 TF 造成死循环。
2. **变换方向不能弄反。** 存的是 `parent_to_child`，累积时
   `p_parent = R·p_child + t` 逐级往根方向乘。
3. **云台位置要单独走一遍。** 自瞄需要的是"枪口/云台在世界里的位置"，它在链的中间，
   不能拿"相机相对云台的安装偏移"顶替。早期就用错过：日志里的 `gimbal_world` 打出来是
   `(0.060, 0.002, 0.196)`，那是相机安装偏移，不是云台世界坐标；正确值应从 `gimbal_link`
   自己往上走到 `map`。
4. **变换矩阵的轴约定在仿真端已经换过一次。** 仿真内部是 Bevy 的 Y-up，发布 TF 时统一乘了
   `M_ALIGN_MAT3` 换成 ROS 的约定；所以节点这边拿到的四元数可以直接用，不需要再自己换轴。

现在节点里并存两条位姿路径，用途不同：

- **跟踪用**：`PoseBuffer` + 图像时间戳插值，保证每帧观测和姿态同刻。
- **自瞄用**：`tf_buffer_->lookupTransform(map, camera_frame, 图像时间戳)`，图像时间戳查不到时
  退到最新一条，再失败就发 `distance = -1`。

## 五、问题四：自瞄一开云台就飞

**现象**：打开 F5 自瞄后云台直接甩到天花板或反方向，相机看不到装甲板，于是自瞄再无输出，
形成"越飞越没数据"的死循环。

**怎么定位的**：不再去猜坐标系，而是把控制链路**两端**的实际值打出来——
自瞄发给 PID 的目标角（`target`）、云台本地欧拉角（`local`）、云台世界姿态（`gimbal_world`）、
枪口世界姿态（`muzzle_world`），每收到一条指令打一行：

```
target=(86.75,90.21) local=(90.41,-31.91) gimbal_world=(101.11,-31.91) muzzle_world=(-78.89,-83.09)
```

读法：

- `local` 与 `gimbal_world` 的 pitch **完全一致**（都是 -31.91），说明云台确实低头了，
  不是本地角/世界角换算出来的假象 → 排除坐标系问题。
- `target` 的 pitch 是从竖直轴量起的，90.21 换成离水平是 **+0.21°**，也就是目标几乎水平。
  两端都合理，却差了 32° → 问题只可能在中间的换算。
- 这 32° 已经逼近 `gimbal_pitch_limit = 0.785 rad ≈ 45°`，所以 PID 长期饱和，表现为"飞"。

**根因**：仿真 `GimbalAimTarget::from_solver_degrees(yaw, pitch)` 里写的是 `pitch - 90°`。
但仿真枪口方向由 `gimbal_rotation * SHOT_DIRECTION.rotation * Vec3::Y` 给出，而
`SHOT_DIRECTION` 这个节点自身带一个约 -65° 的绕 X 安装旋转，要让枪口水平，绕 X 需要 **-90°**，
不是 0°。于是"目标水平"被仿真理解成"正上方"，误差恒差 90°。

**解决**：换算常数改为 `pitch_deg - 180°`。视觉端不动——它发的 `pitch` 是"从竖直轴量起的
角度，水平为 90°"，这个约定和仿真文档一致，错的是仿真这行常数。

**这里的教训**：控制类问题先对齐目标值与反馈值，再谈坐标系。本地角与世界角一致，
就说明坐标系没问题；两者一致却和目标差一个固定角，才回头查消费方的换算。

## 六、自瞄点是怎么选出来的（宏观）

1. **只打本帧实际观测到的那一面。**
   跟踪器会给四面都算出中心（同一套状态，转角相差 90°），但 `r/l/h` 在单板帧下不可观测，
   外推出来的另外三面可能跑到车心另一侧甚至相机背后。所以瞄准点取 `report.last_face`
   对应的那一面。
2. **换算到相机系做合法性检查**：必须在相机前方（`z > 0.1`）、距离不超过 `aim_distance_max_m`。
   不满足就当作没有目标，发 `distance = -1`，让仿真撤掉 PID 目标。
3. **转到 map 系**：用图像时刻的 `map←camera` 变换，把板心从相机系转到世界系。
4. **方向从云台指向目标**，不是从世界原点指向目标：`direction_map = point_map - gimbal_world_`。
5. **出角**：`yaw = atan2(y, x)`，`pitch = 90° - atan2(z, 水平距离)`。
6. **distance** 用相机到目标的直线距离；`fire_advice` 要求距离在限内、且 pitch 与 90° 的偏差
   小于 `aim_fire_angle_deg`。
7. 没有收敛目标、查 TF 失败、方向退化，都会发一条 `distance = -1`，这是"让下位机松手"的信号。

## 七、当前参数与判据

| 参数 | 当前值 | 作用 |
|---|---|---|
| `pose_hold_s` | 0.03 s | 图像晚于最后一条姿态时允许顶替的时间窗 |
| `radius_init_m` | 0.2 m | 半径初值，只在初始化用 |
| `min_detect_count` | 5 | 连续确认帧数 |
| `max_temp_lost_count` | 25 | 短时丢帧容忍 |
| `center_gate_px` / `corner_gate_px` | 100 / 140 | 关联门 |
| `angle_gate_rad` / `perimeter_ratio_gate` | 0.8 / 0.6 | 关联门 |
| `nis_failure_ratio` | 0.8 | 最近 100 次更新的 NIS 失败率上限 |
| `aim_fire_angle_deg` | 1.5° | 允许开火的偏角 |
| `aim_distance_max_m` | 8.0 m | 允许开火的距离 |

状态机：`lost → detecting → tracking → temp_lost → lost`。发散由两条判据兜底：
NIS 失败率超限，或连续 5 次撞半径/第二半径的几何边界。

## 八、当前还留着的诊断

`log_window` 每 2 秒打一组：FPS、检测数、状态机、四门分项（每个候选 × 每个面的
`norm / center / corner / angle / perimeter` 与是否过门）、观测计数
（`image / ypda / limit_clamps / pose_missing`）、姿态时序（`pose offset` 的均值与极值）、
EKF 状态与协方差对角、四面世界坐标、观测点在相机系的位置。

这组日志是当前定位问题的主要依据：单板不收敛看 `r/l/h` 与四个面是否重合，
时间戳问题看 `pose offset` 与 `pose_missing`，关联问题看四门分项，
控制问题看 `target` 与 `local` 的差。

## 九、部署到实车要改的地方

跟踪器本身不持有内参，每帧由 `VisionNode` 通过参数传进来（`tracker_->Update(..., *camera_, ...)`），
`camera_` 只从 `/vision/camera_info` 写入（`vision_node.hpp:230-253`）。这条通路是为仿真定的：
仿真端自己发 `camera_info`，所以节点不能把内参写死。

上实车时相机不发这个话题（或发的不是你标定的那一份），`camera_` 会一直是空的，
`on_image` 每帧打印“还没收到内参，跳过本帧”并直接返回，检测、跟踪、自瞄全部不会启动。

要改的就是内参来源，两种做法：

| 做法 | 改哪里 | 注意 |
| --- | --- | --- |
| 实车相机节点也发 `/camera_info` | 相机驱动侧，跟踪链路一行不改 | 确认它发的就是实机标定的 `K/D`，而不是驱动默认值 |
| 内参写进参数文件 | `vision_node.hpp` 的 `read_parameters` 与 `on_camera_info`，`project/params/vision.yaml` 加七个数 | 实机标定的 `fx=1799.5`、仿真 `fx=1738.4`，差 3.4%，用错距离系统性偏 3.4% |

另外两处同样依赖仿真约定：

- **图像编码**：`CameraNode` 按 `encoding` 分支把 `rgb8` 转 `bgr8`（`camera_node.hpp:95-115`）。
  实车驱动若直接发 `bgr8`，这一步只是去行尾填充；若发别的编码（如 `mono8`、`yuv422`），会被整帧丢弃。
- **时间戳**：`dt` 与帧龄全用 `header.stamp`（`vision_node.hpp:271-282`）。仿真器不发 `/clock`，
  launch 里默认 `use_sim_time:=false`；实车若无独立时钟源，保持 `false` 即可。

## 十、结论

- 单板只能约束车心的两个自由度和转角，形状量必须留给多板帧。
- 姿态必须按图像时间戳插值，不能拿最新值；查不到就丢帧。
- TF 是逐级拼接的，方向、父子关系、云台位置都要单独确认。
- 自瞄角度错误先看目标与反馈两端的数，本地角与世界角一致就不是坐标系问题。
- 诊断输出不能被功能开关挡住——故障恰恰发生在功能打开之后。
