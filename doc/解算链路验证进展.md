## 二、P1：PnP 本身没问题

实测（多轮，云台静止）：

```
reproj = 0.07 ~ 0.11 px
depth  = 0.09 ~ 0.23 m
```

`reproj` 是 PnP 解出的位姿投回像素与检测四点的平均误差。0.1 px 意味着 PnP 对检测角点的
拟合几乎完美，**求解环节可以排除**。

### 修掉的真 bug：IPPE 双解未选择

`SolvePose` 原来直接调 `cv::solvePnP(..., SOLVEPNP_IPPE)`，只取返回的其中一个解。
IPPE 对共面四点有两个解（板正面朝相机 / 背面朝相机），选哪个取决于板尺寸与姿态，没有保证。

合成数据验证（真值板宽 0.140 m、距离 4.5 m、yaw 0.5 rad）：

| 假设板宽 | 解出 z | reproj |
| ---: | ---: | ---: |
| 0.135 | +4.374 | 0.005 px |
| 0.140 | −4.663 | 32.6 px |

板宽偏小反而给出干净正解，板宽"正确"时两个解都不在相机前方。

改法：`solvePnPGeneric` 取双解，优先选 `tvec.z > 0` 的，两个都不在前方时按重投影误差取小的
（返回空会让调用方整帧丢观测，比给一个可疑解更糟）。见 `armor_pose.cpp` 的 `SolvePose`。

### 板宽结论被推翻

曾按 `scale = |t_pnp| / |t_truth|` 稳定在 0.965 推断小装甲板宽应为 0.140 m。**这个推断是错的**：

- `scale` 的分子分母都从相机原点量，比值对板宽不敏感
- 改成 0.140 后 `scale` 从 0.9642 变到 0.9642，没有变化
- 合成数据表明 0.140 会让 IPPE 返回背面解

已改回 `kSmallArmorWidthM = 0.135`（照参考 `solver.cpp:14-16`）。

### `lat` 指标不可用

`pnp lat = 45 ~ 55 mm` 曾长期被判为超标。实际它是"PnP 板心"与"仿真 `armor_N` 参考点"的距离，
而后者是模型里的 `ARMOR/CENTER` 节点：

- 仿真自己画 marker 时（`plugin.rs:236-240`）只取 CENTER 的**位置**，旋转被整个替换掉
- 说明作者也不认 CENTER 的朝向
- 位置同样不是四点几何中心

`truth_reproj` 拆分显示 `shift ≈ 16 px（50 mm）`、`residual ≈ 12 px（38 mm）`，两者都大。
**因此 `lat` 不能当 PnP 精度判据**，测量口径已删除（`scale`、`width_measured`、`width_implied`、
`truth_reproj`、`calib` 全部移除）。

## 三、P2：时间同步是当前唯一未解问题

### 已排除：TF 传输延迟

新增测量 `tf_gap`（相邻 TF 到达间隔）与 `tf_stamp_gap`（相邻 TF 仿真时间戳差）：

```
tf_gap       = 8.3 ~ 10.6 ms
tf_stamp_gap = 8.6 ~ 9.6 ms
tf_delay     = 40 ~ 101 ms
```

两者几乎相等，说明仿真以约 113 Hz 均匀发布、消息均匀到达，**没有排队**。`tf_delay` 是一个
固定的单条消息滞后，而 `PoseBuffer` 按消息自带的 `header.stamp` 插值，**滞后不影响数值**。

### 真正的问题：`pose offset`

```
pose offset avg = 5 ~ 50 ms
pose offset max = 45 ~ 121 ms
pose_missing    = 11 ~ 30 帧/秒（约 20~40%）
```

`pose offset` 是"图像时间戳 − 最新姿态样本时刻"。仿真侧图像 `stamp` 在**快照创建时**打
（`ros2/capture.rs:90`），而图像数据异步回读后才发布，这个时差就是 `age = 50 ~ 65 ms` 的来源。

云台静止时，60 ms 前的姿态和现在几乎一样，误差为 0。
云台以 7.42 rad/s 转动时，40 ms 就是 **17°**——观测被系统性搬动十几度，EKF 只能用车心平移去解释。

### `pose_hold_s` 调整失败

把 `pose_hold_s` 从 0.03 提到 0.08 试图减少丢帧，结果适得其反：

| | hold=0.03 | hold=0.08 |
| --- | ---: | ---: |
| `pose_missing` | 19~30 | 14~17 |
| `tf_delay` | 44~66 ms | 65~92 ms |
| `pose offset max` | 45~65 ms | 95~121 ms |

形成闭环：处理帧变多 → `on_tf` 更多排在 `on_image` 后面 → `tf_delay` 变长 → `pose offset` 变大
→ 又出现新的丢帧。且 `pose offset max = 121 ms` 已超过 `hold = 80 ms`，仍然丢。

**该改法不成立。** 当前值仍是 0.08，需要退回或改用多线程 executor。

## 四、云台静止 vs 云台转动：对照

同一套代码、同一次会话，唯一差别是自瞄键是否按下（云台是否跟指令转）：

| 指标 | 云台静止 | 云台转动 |
| --- | ---: | ---: |
| `drift1s` | 0.002 ~ 0.089 m | 0.187 / 1.125 / 3.090 / 6.258 m |
| `vel` | < 0.2 m/s | 7.21 / 8.00 m/s |
| `r` | 0.203 ~ 0.220 m | 0.050 / 0.118 / 0.150 / 0.291 / 0.500 m（撞钳制边界） |
| `nis_rate` | 0.00 | 0.24 ~ 0.70 |
| `resid` | 0.4 ~ 2.6 px | 15 ~ 48 px |
| `resets` | 3 | 2 ~ 3（`reset=nis`） |
| `pose_missing` | 14 ~ 24 | 11 ~ 18 |
| `tf_delay` | 65 ~ 92 ms | 62 ~ 101 ms |

**时间链路两个场景几乎一样**，所以不是 TF 传输问题；`resid` 涨 20 倍才是症状本身。
`vel` 到 8 m/s、`r` 撞 0.05/0.50 边界、`angle` 跳到 213°——EKF 把"相机在转"当成了"车在飞"。

## 五、P3 / P4：滤波器参数

### `point_sigma_px` 定为 4.0

三轮实测：

| `point_sigma_px` | `resid` | `nis` | `nis_rate` |
| ---: | ---: | ---: | ---: |
| 8.0 | 1.0~1.4 px | 0.10~0.18 | 0.03 |
| 2.0 | 5.1~7.4 px | 23~61 | 0.24~0.30 |
| **4.0** | 0.7~5.1 px | 0.17~8.56 | **0.04~0.09** |

8 太小信观测、2 太大，4.0 让 `NIS` 落到期望值 8 附近。

### 初始协方差 P0 按参考重定

`vehicle_ekf.cpp` 初始化改为参考 `set_target` 的普通车取值：

| 状态 | 原 σ² | 原 σ | 新 σ² | 新 σ |
| --- | ---: | ---: | ---: | ---: |
| 位置 | 0.01 | 0.10 m | 1.0 | 1.0 m |
| 速度 | 0.01 | 0.10 m/s | 64 | 8.0 m/s |
| 角度 | 0.09 | 0.30 rad | 0.4 | 0.63 rad |
| 角速度 | 0.25 | 0.50 rad/s | 100 | 10.0 rad/s |
| 半径 | 0.04 | 0.20 m | 1.0 | 1.0 m |

关键在角速度：原来 σ=0.5 rad/s，而目标实际转速 7.42 rad/s，差 15σ，锁定后只能靠观测慢慢拉。

### 新增诊断：残差 RMS

`VehicleEKF::UpdateImagePoints` 在 `correct()` 之前算"观测 − 预测"的逐点均方根，存进
`Snapshot::residual_rms_px`，日志里是 `track` 行的 `resid=`。

和 NIS 配合才能分清模型问题与状态问题：

| NIS | 残差 RMS | 结论 |
| --- | --- | --- |
| 大 | 大 | 状态偏了 |
| 大 | 正常 | 协方差假设过紧 |
| 小 | 大 | 观测噪声给太大 |
| 正常 | 正常 | 模型自洽 |

### 新增诊断：车心 1 s 漂移

`vision_node` 在跟踪器建目标时记下车心与时刻，满 1 s 后算位移，日志里是 `drift1s`。
跟踪器回到 `lost`（含 `Reset`）时丢弃起点，避免把换目标的位移算进来。

## 六、P5：单板帧冻结形状量

### 已做

`UpdateImagePoints` 修正完成后，若 `estimate_shape == false`（单板帧），把 `r` / `l` / `h`
写回修正前的值（协方差保留，后续多板帧仍能修正）。

原来单板帧虽然不把 `r/l/h` 放进雅可比，但 `correct()` 修正 `cx/cy/angle` 时，协方差与 `r` 的
相关性仍会把它带走。

### 实测效果：无效

改动前后 `drift1s` 分布没有变化（0.007~0.82 对 0.05~1.22）。污染源不在单板帧的方差相关性。
改动保留（有益无害），但漂移的账记在 P2。

### 面序本身是物理换板，不是关联错标

`face switch` 每 0.21 s 一次，正好等于 `90° / 7.42 rad/s`。换面帧的关联代价是新面 0.19、
旧面 4.33，差 20 倍。说明每次都是真的换到另一块物理板。

## 七、P6：瞄准面选择（已实现，未实跑）

### 原来错在哪

`SelectAimPointCamera` 直接用 `tracker.Report().last_face`——那是**本帧检测匹配到的面**。
单板帧永远只有一块板被观测到，所以瞄准点只能跟着物理换板跳，每跳一次差
`2·r·sin45° = 0.283 m`，提前量无从谈起。

### 现在的做法（照参考 `Planner::choose_aim_point`）

新增 `AimPublisher::SelectAimFace`，从 EKF 外推的四个面里选：

```
center_yaw = atan2(车心 − 云台)
delta[i]   = 该面法向角 − center_yaw
```

- **慢转（|ω| ≤ 2 rad/s）**：`|delta| ≤ 60°` 的算可射击。多于一个时锁存，选 `|delta|` 小的，
  两块板卡在边界上时不会来回跳；只剩一块时立即退出锁定。
- **小陀螺**：`|delta| ≤ 55°` 里找 ω>0 且 `delta < 20°` 的板（或 ω<0 且 `delta > −20°`），
  即"正要转出"的那块——命中概率更高。

新增参数（`vision.yaml`）：`aim_sector_deg`、`coming_angle_deg`、`leaving_angle_deg`、
`spin_omega_threshold`。

### 可视化

`draw_targets` 改为三色：**瞄准面红**、本帧匹配面绿、其余两面黄。瞄准面与匹配面经常不同。

### 需要澄清的一点

参考工程里 **tinyMPC 不参与选面**。`planner.cpp` 的流程是：

```text
choose_aim_point(target, lock_id)      // 选面：纯几何，用 armor_xyza_list + ekf_x[7]
  → solve_xyza(xyza, bullet_speed, R)  // 对选中的面算弹道与提前量
  → tinyMPC 规划 yaw/pitch 轨迹
```

MPC 只做"给定一个板的位置，规划云台怎么转过去"。

## 八、MPC 与下位机接口（查证结论）

参考工程 `auto_aim_runtime.cpp:345`：

```cpp
const double absolute_yaw = state.yaw + plan.yaw;
// Talos consumes an absolute solver target; the hardware planner command is relative.
```

`VisionToGimbal` 帧（`io/gimbal/gimbal.hpp`）字段：

```cpp
uint8_t mode;      // 0 不控制 / 1 控制不开火 / 2 控制且开火
float yaw;         // 相对云台系的增量
float yaw_vel;     // 前馈
float yaw_acc;     // 前馈
float pitch;
float pitch_vel;
float pitch_acc;
```

**上位机发的是相对角 + 速度/加速度前馈，不是角速度序列。** 下位机按"目标 = 当前 yaw + 下发 yaw"
解释，自己做位置环。

这一点对仿真有利：`/rm_gimbal/cmd` 的 `yaw` / `pitch` 也是角度，协议对得上，MPC 可以直接落地，
不需要改仿真接口。

## 九、还没做

1. **P2 的修法**：让图像时刻与姿态时刻真正对齐。候选方案是改 `MultiThreadedExecutor` +
   Reentrant callback group，让 `on_tf` 不再排在 `on_image` 后面；或退回 `pose_hold_s = 0.03`。
2. **P6 实跑验证**：红色瞄准面是否稳定停在正对我们的那个面上、不跟着绿框跳。
3. **P7 提前量**：子弹飞行时间 `t = 距离 / 弹速`（4 m、25 m/s ≈ 160 ms），期间目标转
   `ω·t = 68°`。瞄准点要取 `t` 时刻的面心，不是当前面心。
4. **P7 弹道**：重力下坠 `½gt² = 0.126 m`，pitch 要抬。`SolveAim` 里已有部分。
5. **MPC**：按参考的 `tiny_setup` + `tiny_solve` 做 yaw/pitch 轨迹规划，输出相对角 + 前馈。
